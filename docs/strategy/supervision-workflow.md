# 監修ワークフロー（合格者レビュー）

> 問題データの品質を担保する唯一の手段は、電験合格者による監修です。コードは検算・検証
> （`solver_checked` / `clean_answer` / `physically_valid`）まではできますが、
> 「この問題は試験問題として妥当か」は人間にしか判定できません。
> 本書はその作業手順書です。

## 0. 2つの監修レイヤ

問題データは2つのプールに分かれており、**それぞれ別の監修コマンドを使います**。

| プール | 件数 | status | 監修の単位 | コマンド |
|---|---|---|---|---|
| `data/problems/` | 52 | validated | **問題1件ずつ** | `supervision:status` 系 |
| `web/problems.json`（配信中） | 約 9,354 | draft | **テンプレ1件ずつ** | `supervision:templates` 系 |

配信中の約 9,354 問は 151 テンプレから生成されているため、1問ずつは追えません。
**テンプレ1件を監修すれば、そこから出る全問題（平均約62問・最大300問）がまとめて担保されます。**
まずテンプレ監修でカバレッジを稼ぎ、代表問題 52 件は個別監修で仕上げるのが効率的です。

## 1. テンプレ監修（レバレッジが最大）

### 手順

```sh
# ① 状況を見る（レバレッジ順のキューが出る）
npm run supervision:templates

# ② レビューパケットを書き出す（out/ は .gitignore 済み）
npm run supervision:templates:packet -- --out out/template-packet.md

# ③ 合格と判断したテンプレを台帳に記録する
npm run supervision:templates:mark -- --supervisor "あなたの名前" 三相交流電力 力率改善
```

`--note "条件付き: レンジ上限は要検討"` や `--date 2026-08-06` も指定できます。

150件を一度に見るのは非現実的なので、パケットは絞り込めます。

```sh
# 法規から20件ずつ進める（推奨の進め方）
npm run supervision:templates:packet -- --subject 法規 --limit 20 --out out/houki.md
# 変更で無効化されたものだけ再監修する
npm run supervision:templates:packet -- --stale-only --out out/stale.md
```

絞り込んだ場合は「該当 N 件中 M 件を出力」がパケット冒頭に必ず出ます（黙って切り詰めません）。

### パケットに載る情報

テンプレ1件につき、監修に必要なものが揃っています。

- **担保できる問題数** — この1件を監修すると何問がカバーされるか
- **パラメータの現実的レンジ**（`realistic_range`）— 実機・実系統としてありうる値か
- **出題分野メタ**（`pastExam`）— 分野・頻度・代表年度
- **生成サンプル3件** — 実際に出荷されるのと同じ数列で生成した問題文・選択肢・正解・解説・誤答の想定
- **チェックリスト7項目**と記入欄

### チェックリスト

1. 計算式そのものが物理的に正しいか（次元・係数・符号）
2. パラメータの現実的レンジが実機・実系統としてありうる値か
3. 生成サンプルの答えが独立計算と一致するか（サンプル全件を検算）
4. 解説の筋道が飛躍なく、最終値に単位が付いているか
5. 誤答選択肢が「実際に起こる典型ミス」に対応しているか
6. 出題分野メタの分野・頻度が実際の出題傾向と整合するか
7. 法規・制度は最新の改正に整合するか

### 【重要】監修はテンプレを編集すると自動的に無効になる

テンプレはコードなので、監修後に式やレンジを編集すれば監修の前提は崩れます。
そこで監修時に **テンプレの「振る舞いのフィンガープリント」** を台帳に記録し、
現在の振る舞いと一致しなくなったものを **要再監修（stale）** として必ず表示します。

```
- 要再監修（監修後にテンプレが変更された）: 1
⚠️ 要再監修が 1 件あります。監修後にテンプレが変更されており、以前の監修は前提が崩れています。
- [理論] 三相交流電力 ★2 🔁要再監修（34問を担保）
```

フィンガープリントは**ソースコードの文字列ではなく、決定論的に生成した問題そのもの**から作ります。

| 変更 | 監修は？ |
|---|---|
| コメント・変数名の変更 | **維持される**（監修者が見たものは変わっていない） |
| 計算式・係数の変更 | **無効化**（要再監修） |
| `realistic_range` の変更 | **無効化**（レンジは監修の主要な確認事項） |
| 難易度・科目・出題分野メタの変更 | **無効化** |
| 解説文・選択肢の変更 | **無効化** |

要再監修になっても台帳の記録は消えません（誰がいつ監修したかは残る）。
キューでは要再監修が最優先で先頭に来ます — 一度監修した前提が崩れている状態は、
未監修より危険だからです。

### 見落とし防止（品質ゲートへの統合）

要再監修は専用コマンドを叩かないと気づけないと意味がないので、**通常の監査にも載ります**。

```sh
npm run audit:status          # - templates supervised: 20/151 (13.2%) / stale: 3
npm run audit:status:strict   # 要再監修・孤児があれば exit 1（リリースゲート）
```

台帳にあるのに実在しない topic（テンプレの改名・削除で取り残された記録）は
**孤児**として検出し、こちらも同様にリリースを止めます。

### 監修は問題データへ伝播する

`npm run build:problems` は台帳を読み、**監修済みテンプレから生成された問題に
`validation.supervisor_checked: true` を立てます**（要再監修・未監修のテンプレからは立てません）。

つまりテンプレを編集すると、次のビルドで生成問題の監修フラグが自動的に外れます。
監修の主張が実データと食い違ったまま出荷されることがありません。
台帳が空のあいだは生成物は完全に不変です（差分ゼロ）。

### 台帳

`data/supervision/templates.json` にコミットします。

```json
{
  "version": 1,
  "entries": [
    {
      "topic": "三相交流電力",
      "fingerprint": "2ae685aa9b149b8c",
      "supervisor": "山田太郎",
      "at": "2026-08-06",
      "note": "任意のコメント"
    }
  ]
}
```

⚠️ この記録は「人間（電験合格者）が監修した」という主張です。**書き込んだ人が責任を負います。**
コードは監修の中身を判定しません（できません）。

## 2. 問題単位の監修（代表52問）

```sh
npm run supervision:status                          # 状況
npm run supervision:packet -- --out out/packet.md   # レビューパケット
npm run supervision:mark -- T-0001 T-0002           # 合格フラグを立てる
```

`data/problems/<id>.json` の `validation.supervisor_checked` を安全に書き換えます
（他フィールドと整形は不変・冪等）。`validated` 段階の問題だけが対象で、
`draft` の問題を誤って監修済みにはできません。

チェック観点は6つ（数値の独立再計算 / 出典の妥当性 / 物理的成立性 / 誤答選択肢 /
法規の改正整合 / 著作権上の引き写し）。

## 3. 進め方（実データにもとづく計画）

### レバレッジの実測

テンプレ1件を監修したときに担保できる問題数は、科目によって4倍以上の差があります。

| 科目 | テンプレ数 | 問題数 | 1件あたり |
|---|---|---|---|
| 理論 | 34 | 2,628 | **77問** |
| 電力管理 | 24 | 1,832 | 76問 |
| 機械 | 28 | 2,002 | 72問 |
| 機械制御 | 22 | 1,259 | 57問 |
| 電力 | 23 | 1,268 | 55問 |
| **法規** | 20 | 365 | **18問** |

⚠️ **法規は最もレバレッジが低い**（20テンプレ全部やっても365問＝全体の3.9%）。
改正リスクが高いので優先したくなりますが、量では稼げないことを承知の上で選ぶこと。
一方、キュー上位10件（各300問）だけで **約3,000問＝32%** が埋まります。

### 推奨する順番

1. **キュー上位10件**（各300問・計約32%）— まずカバレッジを一気に立ち上げる。
2. **法規 20 件**（計365問）— 量は少ないが改正リスクを潰す。1バッチで片付く。
3. **二次記述系 46 件**（電力管理24＋機械制御22）— 解説（`defaultSolution`）の質が
   部分点ルーブリック（`lib/curriculum/rubric.ts`）の配点にそのまま効くため、学習体験への影響が大きい。
4. **残りをキュー順**（レバレッジ順に並んでいる）。
5. **代表 52 問の個別監修は仕上げに。** テンプレ監修が済んでいれば確認は軽くなります。

### 最初の1回（30分想定）

いきなり20件出さず、**1件だけ**やって手順を体感するところから。

```sh
npm run supervision:templates:packet -- --limit 1 --out out/first.md
```

出てくるのはキュー先頭の1件です。パケットに式・レンジ・生成サンプル3件が載っているので、
やることは実質3つだけ:

1. サンプル3件の答えを電卓で独立に検算する
2. `realistic_range` が実機・実系統としてありうる値か見る
3. 解説の筋道と、最終値に単位が付いているかを確認する

問題なければ記録します。

```sh
npm run supervision:templates:mark -- --supervisor "あなたの名前" <topic>
npm run supervision:templates   # カバレッジが動いたことを確認
```

1件目で「1件あたり何分か」が分かるので、そこで残りの計画を立て直してください。

### 2回目以降（バッチで回す）

```sh
npm run supervision:templates:packet -- --limit 10 --out out/batch.md          # 上位10件
npm run supervision:templates:packet -- --subject 法規 --limit 20 --out out/houki.md
npm run supervision:templates:mark -- --supervisor "名前" <topic1> <topic2> ...  # まとめて記録
```

`mark` は複数 topic を一度に受け付けます。台帳は topic 順に整列されるので差分が読みやすく、
PR レビューで「誰が何を監修したか」がそのまま追えます。

### 進捗の確認とコミット

- 監修のたびに `data/supervision/templates.json` が更新されるので、**コミットして残す**こと。
- `npm run audit:status` にも `templates supervised: N/151` の行が出ます。
- テンプレを編集したら、次のビルドで生成問題の監修フラグが自動的に外れます。
  `npm run build:problems` を回して `web/problems.json` の差分もコミットしてください。
